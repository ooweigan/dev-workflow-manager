# Commit Message 协议 v1

## 完整格式

项目没有更具体的格式规定时，严格使用以下顺序、大小写和空行。正文默认建议使用中文，便于团队阅读；这只是写作建议，不设语言校验，也不作为提交通过条件。项目已有语言习惯时跟随项目，字段名固定英文。

```text
<type>(<scope>): <summary>

Description:
- <实际修改及必要原因>

Page-Path:
- <用户可操作的入口 → 页面 → 操作>

Platforms:
- <本次实际修改的目标端>

Issue:
- <内部任务编号或带上下文的链接>

Verification:
- <目标端：实际检查及结果，或未执行：具体原因>

AUTHOR:<author>;XQBH:<external-requirement>;NOTES:<summary>
```

除标题和元数据行外，每个区块至少一条 `- ` 列表项。多个路径、任务、目标端和验证项各占一行。字段不可空缺。路由和模块可在 Description 的独立列表项中补充，不增设模糊的同义字段。

## 标题

- 格式为 `type(scope): summary`，scope 必填，使用稳定的业务模块或目标端，如 `policy`、`login`、`ios`、`build`；不要把文件名、任务号或整个目录当 scope。
- type 为 `feat`、`fix`、`perf`、`refactor`、`file`、`style`、`docs`、`test`、`chore`、`build`、`ci`、`revert`。
- `file` 是本团队的自定义资源类型，用于仅静态资源更新；`style` 只表示不改变语义的代码格式调整。界面样式修复按目的使用 `fix`，新增视觉功能使用 `feat`。
- summary 简明描述结果，不写“修改文件”“优化代码”等空泛标题，不以句号结尾；不设机械的中文字数上限。
- 存在实际破坏性兼容变更时在 scope 后加 `!`，并在元数据行之前添加 `BREAKING CHANGE:` 区块，列表中描述影响与迁移方式。普通改动不加。

## 各字段语义

- Description：依据暂存 diff，解释修改结果及必要原因，禁止把未实现的计划写进去。
- Page-Path：从需求、实际导航入口、路由配置与页面代码确认。文件路径不能代替操作路径。前端入口无法确认时使用 `- 待确认：<缺少什么依据>` 并向用户说明；这不阻止已授权的提交，但不能宣称字段已确认。非页面变更写 `- N/A：<原因或模块>`。
- Platforms：本次实际修改的端，如 H5、iOS、Android、小程序、shared、tooling。影响端但未修改的内容在任务记录中说明，不能假装都已处理。
- Issue：内部任务编号或外部任务链接，可多条。无登记任务时写 `- N/A：<例如本次为独立维护，未登记任务>`。用户或项目要求必须关联时，先取得或登记真实编号，不能用 N/A 绕过。
- Verification：真实检查及结果。未执行使用 `- 未执行：<检查项及原因>`；失败必须记录失败及影响，是否允许提交按用户授权和项目规则判断。构建通过不能替代设备验收。
- AUTHOR：使用项目指定的真实作者，否则读取当前仓库有效 Git user.name；不可从系统用户名、聊天身份猜测。没有可确认作者时，先准备其余内容，再询问作者；不要擅改 Git 身份。
- XQBH：仅填写真实外部需求编号，多个用 ASCII 逗号分隔；没有外部需求编号固定写 `NONE`。内部 TASK/BUG 编号只放 Issue，不能冒充需求编号。项目强制要求外部编号时，NONE 不视为满足要求。
- NOTES：与标题的 summary 完全相同。

元数据必须是消息最后一行，单行严格使用 ASCII `:` 和 `;`，字段顺序固定为 AUTHOR、XQBH、NOTES，无分隔空格。值不得含 ASCII 分号或换行，避免破坏旧系统解析；summary 中需要分号时改写为逗号。XQBH 的多个编号不能含空白或分号。

## 示例：Bug 修复

以下为虚构格式示例，不可直接当作真实项目证据。

```text
fix(order): 修复订单详情返回后列表筛选条件丢失

Description:
- 返回列表时恢复已选择的筛选条件，避免被初始化逻辑覆盖

Page-Path:
- 订单管理 → 订单列表 → 筛选 → 订单详情 → 返回

Platforms:
- iOS

Issue:
- TASK-20261109-001

Verification:
- iOS：设备手工回归未执行，当前未连接测试设备

AUTHOR:开发者甲;XQBH:NONE;NOTES:修复订单详情返回后列表筛选条件丢失
```

## 示例：非页面维护

```text
build(tooling): 更新构建配置中的产物目录

Description:
- 调整产物输出路径，与现有打包目录保持一致

Page-Path:
- N/A：构建配置

Platforms:
- tooling

Issue:
- N/A：独立构建维护，未登记任务

Verification:
- 未执行：构建环境未就绪，待构建验证

AUTHOR:开发者甲;XQBH:NONE;NOTES:更新构建配置中的产物目录
```

## 执行

读工作区和暂存 diff 后生成消息，写临时文件，运行 `scripts/validate_commit.py`。脚本不访问 Git、不暂存、不提交、不修改文件，只验证完整格式。

代理还须进行语义核实。仅格式通过不能证明页面路径、作者、任务与验证真实。用 `git commit -F <message-file>` 保留真实换行；不要把多行文本或未转义用户内容拼入 shell。提交后读取真实提交哈希及消息，并记录任务关联。禁止仅凭命令已启动便报告成功。
